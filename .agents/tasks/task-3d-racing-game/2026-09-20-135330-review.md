# Apex Circuit: no-build 3D browser racing prototype (v1)

A greenfield, no-build Three.js + Cannon-es racing prototype delivered across four features: an engine core (fixed-step loop, renderer, chase camera, keyboard input), a raycast-vehicle physics car, a designed circuit with ordered-checkpoint lap logic and a race director, and an environment/feedback polish pass (procedural sky, drift skid marks, mid-race respawn, a systems-registry extension seam). The design splits browser-only code (imports `three`/`cannon-es` via an importmap resolved in the end user's browser) from pure `game/logic/` helpers that carry the lap, drift, camera, and formatting math so they can be unit-tested offline. Input feeds physics feeds render at a fixed 60 Hz, controls are gated by the race phase, and 43 offline tests plus a syntax/structure check pass cleanly.

Watch for: the vehicle/handling/rendering path cannot be exercised headless in this sandbox (no browser, CDN unreachable), so all confidence about in-browser feel is architectural, not observed (confirmed, documented by the author). Two behavioral edges are worth a look before shipping: a mid-race respawn drops the car exactly onto the last gate's centerline point rather than a spawn offset behind it (likely), and `Car.update` runs `sync()` against pre-step transforms before the world is stepped (confirmed, benign but wasteful). No blocking defects found.

**Verdict**: APPROVED

## High-level view

The architecture's spine is a separation between impure engine/game modules and a pure `game/logic/` layer. Everything testable without a GPU or physics engine (lap sequencing, gate-crossing geometry, drift detection, camera damping, time formatting, loop timing) lives in pure modules that the impure layers consume, so the tests hit production code paths rather than reimplementations.

Lap integrity is enforced in `lap.js` through an ordered state machine plus a forward-only segment/plane crossing test. Out-of-order gates, re-touched gates, and start/finish crossings without clearing intermediates are all rejected, closing the obvious corner-cutting exploits. The checkpoint tracker tests only the next expected gate and gate 0 each step, avoiding same-step false positives from distant gates.

The track builds both visual barrier meshes and matching static Cannon bodies from the same offset centerline, so collisions a player sees will resolve in physics. Checkpoint gates are made wider than the road so any on-tarmac car triggers them.

The race director is a compact LOADING to COUNTDOWN to RACING to FINISHED machine that locks controls outside RACING and starts the clock on GO. R recovers a spun car at its last passed gate during a race, and restarts from the countdown on the finish screen.

The loop carries a small ordered systems registry (`addSystem`/`removeSystem`, shared context, fan-out after the core update/render) that gives Phase 2 (AI, audio, minimap, multiple cars) an insertion point without touching the bootstrap. The contract is documented and tested.

The known gaps are environmental: no headless render/e2e coverage is possible here, and the CDN libraries can only load in a real browser. Both are expected and documented.

## Pure-logic split as the testability backbone

Routing every GPU/physics-free computation through `game/logic/` modules that import nothing from Three or Cannon is what makes this prototype verifiable at all in a sandbox with no browser and no network. `lap.js`, `drift.js`, `cameraMath.js`, `format.js`, and `handling.js` are consumed by the impure layers (`checkpoints.js`/`raceState.js`, `car.js`, `camera.js`, `hud.js`) and exercised directly by the tests, so the tests hit the same code paths production uses. `checkpoints.js` claims it imports "only the pure lap.js logic ... so the crossing/registration flow is exercised by the same code path the tests cover," and that holds: `CheckpointTracker` calls `crossedGate` and `registerCheckpoint`, both covered by the lap tests across in-order, out-of-order, re-touch, reverse, off-width, and diagonal cases.

## Ordered-checkpoint lap integrity

Lap counting cannot be cheated through the obvious routes. `registerCheckpoint` advances a single `nextCheckpoint` cursor: intermediate gates are accepted only when `index === state.nextCheckpoint`, gate 0 completes a lap only when `nextCheckpoint` has wrapped back to 0, and any crossing before timing starts is ignored. The tests confirm a skipped gate 2 is rejected, a premature gate-0 crossing credits no lap, and re-touching an already-passed gate 1 is ignored.

Forward-only crossing is enforced geometrically in `crossedGate`: it requires the movement segment to pass from the negative side of the gate plane to the non-negative side (`dPrev < 0 && dCurr >= 0`), so reversing back through a gate never registers, and it bounds the parametric hit point to the gate half-width so passing wide of the gate line does not count. `CheckpointTracker.update` narrows the tested set to just `nextCheckpoint` and gate 0 each step, preventing a distant unrelated gate from falsely triggering in the same frame.

## Track barriers produce matching physics bodies

`_buildBarrierWall` walks the resampled centerline and, per segment, emits both a `THREE.Mesh` and a static `CANNON.Box` with the same center, yaw, and padded length (`len + 0.4` so neighbors overlap and leave no gaps on the outside of curves). Both sides (`outer-left`, `outer-right`) are generated this way and added via `physicsWorld.addBody`, so a car that visually hits a wall collides in physics too. The gate width is `checkpointHalfWidth * 2 = 22 m` against an 18 m road, so any car on the tarmac crosses the gate plane within width. One thing to eyeball in-browser: on the tightest inner radius (the hairpin around z = -64 to -88), an offset of `roadHalfWidth + thickness/2` can make inner-edge segments crowd or self-overlap; it will still collide correctly but may look busy. (possible, needs a visual check)

## Race director phase machine and the GO handoff

`RaceDirector` runs LOADING to COUNTDOWN to RACING to FINISHED and exposes `controlsLocked`, which `main.js` uses to feed a frozen `NEUTRAL_INPUT` outside active racing. The countdown has a subtlety worth noting: `_go()` unlocks controls and starts the race clock at the moment "GO!" is shown, while the phase stays COUNTDOWN for a short `goHoldMs` so the overlay can display "GO!". The guard `!this.controlsLocked && phase !== FINISHED` is what lets checkpoint detection and the race clock begin during that brief GO hold rather than waiting for the RACING flip. The asymmetry between "controls unlocked" and "phase === RACING" is easy to miss when reading the getters, since `currentLapTimeMs` returns 0 until `phase === RACING` even though timing has already started. HUD-only, not a scoring bug, but flag it for anyone extending the director. (confirmed)

## Respawn and restart wiring

R is edge-detected in `input.js` (latched so one press yields one reset even across multiple fixed substeps in a frame), and `main.js` branches on phase: on FINISHED it respawns at the grid and calls `race.restart()` (rebuild lap state, return to LOADING, re-enter the countdown); mid-race it teleports to `race.lastCheckpointPose` with velocity zeroed and re-seeds the tracker's previous position so the next crossing test starts clean.

The respawn pose is the one behavioral wrinkle. `lastCheckpointPose` returns the gate's own centerline point (`{ x: gate.position.x, z: gate.position.z }`) and the gate-forward heading, dropping the car straddling the checkpoint line it just cleared, with no backward offset. The grid spawn, by contrast, nudges 6 m back along `-forward` in `_computeSpawn` so the car crosses gate 0 cleanly after the countdown. Because the last passed gate is already cleared (`nextCheckpoint` has advanced) and `seedPosition` re-seeds `_prev` to that same point, it will not double-count, but recovering exactly on the line is an awkward player experience and risks the car nosing into gate geometry visually. A small `-forward` offset would match the grid-spawn treatment. (likely)

## Drift feedback chain

The pooled skid system in `skidmarks.js` is fixed-capacity and round-robin, so decal count is bounded and nothing leaks, and `clear()` is called on every respawn so marks do not linger through a teleport. Both the smoke sprite and the sky/gradient textures are generated on a canvas with an explicit non-browser fallback (`return null`), so the pure-logic tests and syntax checks are unaffected by the absence of a DOM.

The rolling-resistance value applied while coasting, `brakeForce = 2` in `car.update`, is the one tunable that escaped `CONFIG`. Everything else in the handling feel is in the frozen config object; this constant should join it so the "single source of truth" claim in `config.js` stays literally true. (confirmed)

## Update/step/sync ordering

`main.js` runs the correct per-step sequence: set controls (`car.update`), step physics, then `car.sync()` to copy solved transforms onto the visuals. But `Car.update` also calls `this.sync()` at its own end, before the world has been stepped, so that inner sync copies last frame's transforms and is immediately superseded by the post-step sync in `main.js`. It is harmless (the later sync wins) but wasteful, and it muddies the contract: the method's own doc comment hedges about who is responsible for stepping. Dropping the internal `sync()` and relying on the caller's post-step sync would make the data flow unambiguous. (confirmed)

## Fixed-step loop and the systems seam

`loop.js` is an accumulator loop with an injectable time source (`now`/`raf`/`cancel`) so it can be driven deterministically in tests, and it clamps oversized frame gaps to `step * maxSubSteps` to avoid a catch-up burst after a backgrounded tab. On top of the core `onUpdate`/`onRender` it keeps an ordered systems list that fans out after the core callbacks, sharing one `context` object. The tests confirm ordering (core before systems), once-per-frame render fan-out, duplicate rejection, removal, initial-array construction, and safe skipping of a system missing a method. The planned AI/audio/minimap/multi-car systems each map onto `{ update(dt, ctx), render(alpha, ctx) }` reading `ctx.car`/`ctx.track`/`ctx.race`.

## Test coverage and what is not covered

The 43 tests are substantive, not static: `lap.test.js` drives full multi-lap sequences and would fail if the ordering guard, reverse rejection, width bound, or best-lap tracking were reverted; `drift.test.js` pins the AND-condition in `isDrifting` and the clamped ramp in `driftIntensity`; `loop.test.js` asserts exact step counts and the spiral-of-death clamp; `respawn.test.js` exercises the `lastPassedGateIndex`/`lastCheckpointPose` derivation across all four cursor positions; `logic.test.js` covers the camera damping seam-crossing and time formatting edge cases.

Not tested (and mostly not testable here): the raycast vehicle's actual handling response, collision resolution against barrier bodies, the render pipeline, and any end-to-end drive-a-lap flow. This is a hard environmental limit and is documented in the README's offline note rather than hidden. Before the prototype is called finished it should get one manual browser smoke test on a networked machine, specifically confirming that timing starts when the car first crosses gate 0 after GO, that a full three-lap race reaches the finish panel, and that R recovers a spun car on-track. (confirmed, environmental)

## Documentation and conventions

The README accurately describes the no-install/no-build run paths (Python, `npx serve`, the bundled `serve.mjs`), explains the importmap/CDN dependency and the browser-needs-internet-once caveat, documents the exact controls including R's dual behavior, and points tuning at `config.js`. Run commands match the environment quirks (the `test/**/*.test.js` glob is what works on Node 22 here). The whole tree is free of em-dashes per the stated requirement (verified by byte-level grep).
